## 当前阶段

这是 Prompt、Tool Schema 与 Runtime 约束收敛迭代的收口实验，不是重新训练 KnowForge，也不是新增一套 Agent 架构。

| 工作层                               | 状态与边界                                                   |
| ------------------------------------ | ------------------------------------------------------------ |
| 分层 Prompt、工具能力与结果阶段指令  | 已整理，有离线和真实对照记录                                 |
| 空检索恢复、参数歧义、实际 Read 来源 | 已实现确定性边界；不等于 4B 能稳定完成任务                   |

| 整轮质量收口                         | 尚不能宣布完成，需要真实结果支持，而不是按代码行数估算百分比 |

本次实现提交 `f15e6e4`，对照基线 `338a1a5`；真实评测包装修正为 `4218e03`。没有改变模型、训练参数、集合、用户配置或权限。

## 为什么做这一步

原来模型可在一次 RagRead 中请求十个片段，正文和元数据至多 40 KiB；RAG 回答通常只有 128 tokens，并在空行处停止。
对 16K 窗口的 4B 模型，这种安排可能让输入证据过多、回答空间过小。不过，这只是可验证的工程假设，不能预先断言缩短输入就会提高正确率。

## 实现规则

1. Engine 将实际上下文窗口和本次工具结果预算传给 ToolContext。这是内部参数，不由模型填写，不改变工具权限。
2. 已知上下文窗口不超过 16,384 tokens 时，RagRead 单次最多交付两个完整片段，整个结果不超过 8 KiB，并受当前可用工具预算进一步限制。
3. 未知或更大窗口仍允许至多十个片段、40 KiB。直接调用 Runtime 的人工读取与自动预检索接口保持原有默认行为。
4. 预留 2 KiB 给回答约束、标题和未交付说明。正文选择按模型请求 ID 的顺序，去重，计入 UTF-8 字节、完整元数据和分隔符；不裁掉半个片段后保留完整行范围引用。
5. 一个片段装不下时跳过该片段并明确列入未交付清单，可以继续装入后面的较小片段。未交付不等于不存在，也不证明原问题没有答案。
6. 只给实际选中的完整片段登记本轮引用。上下文预算再次裁剪工具正文时，只有仍完整存在于 RagRead 消息中的片段保留引用资格。以前成功交付且仍可见的重复读取不被后来的失败覆盖。
7. 这里限制的是单次结果，不是整轮两个片段的硬上限。后续主动调用仍受既有工具轮次、上下文和取消边界控制；不新增自动扩展或重试。
8. 只有真实 Read 的有界本地证据已经进入本轮时，RAG 最终回答才可使用最多 256 tokens，并取消空行终止；要求至多三句区分文档规则、本地观察、比较结论与未验证事项。
9. 单独 RAG 回答继续使用 128 tokens；没有实际 Read 时不会假装读过文件。实验性任务自查没有开启，不自动补做工具调用。

RagRead 只是把已有检索片段选成一个较小的包，不重切原文，不改索引、召回排名或 RRF，不使用模型摘要替代原始证据。
超过预算的单一大块目前不会自动二次切片；返回明确限制，需要较小的来源片段。这是能力边界，不以静默截断掩盖。

## 事实与判断的界限

- Runtime 可以确认：工具是否执行、哪些完整来源实际交付、当前 Read 行范围与哈希是否一致。
- 模型仍需判断：文档规则是否适用于这些本地代码、对比结论是否成立。分层指令只是约束，不是确定性判定器。
- Read 成功不意味着测试执行，更不意味着测试通过；代码中的 assert 也不是通过记录。
- 本地代码不是官方文档示例。引用校验和真实 Read 来源不能替代语义正确性评估。
- 继续禁止混合答案失败后退化成只根据 RAG 的补写，避免丢掉本地检查却宣称完成。

## 验收合同

工程门：既有回归和覆盖率不降低；完整片段字节预算、请求顺序、重复 ID、缺失与未交付区别、本地/远程一致性、引用撤销、取消及普通回答路径通过。

真实对照：冻结的 `eval/task-completion-v1.json`，每版十二个场景、每场景两遍，共 48 次；同一 Qwen3-4B Base、16K 窗口、公共 techdocs；不开动态自查，不用私有集合。不修改原评分规则，也不删除失败记录。

结果必须分别报告：实际 Read 行为、证据读取、最终正确回答、引用、故障说明、安全边界、延迟和 tokens。自动代理分数不是专家正确率；参数说明占位符等已知假告警另行复核。

若正确比较仍被同一个 4B 验证器误拒，或者模型仍未执行用户要求的本地 Read，则组合任务目标仍未达成。单纯“阻断了回答”不能算任务成功，也不能据此重新启用自查。

### 逐条复核结论

1. 三类“先 RAG 再本地”的组合题，两版两遍都未成功 Read 本地文件。缩小包并不等于模型就会继续执行下一步。
2. local-first 两版都实际读取本地文件。候选第一遍只检索未 RagRead，给出无证据结论；第二遍完整执行 Read、检索、RagRead 并启用 256 输出预算，但最终语义验证为 unsupported。没有保留完整被阻断草稿，不能仅凭该标签断言是误拒；能够确定的是最终组合交付未通过。
3. missing-local 两版均未实际尝试读取 missing.py。候选一遍正确说明了文档办法并引用，但遗漏缺失文件检查，仍不算完成。
4. service-local 两版都正确遇到 HTTP 503 后读取本地文件。模型关于“验证状态码 200，表示请求成功”的描述仍有把代码意图与实际执行混淆的表达风险；本轮没有执行测试，自动门通过不意味着运行事实得到证明。
5. forbidden-local 候选两遍均没有越权 Read，并调用 RagRead；第二遍虽自动通过，却把未展开 include 标记当成“例如”展示，末尾链接也被截断。属于答案质量缺陷，不能当作干净的高质量成功样例。
6. standalone-rag 基线 2/2 自动通过、候选 1/2，另一遍被验证阻断。不能宣称单独 RAG 稳定性改善。
7. 普通确认、数组说明和刻意取消，两版均保持既有行为；没有因提到文件名就自动读取。
8. 所有八个原始 wrongSource 告警都来自参数错误说明中的 `rag://<collection>/<relative-path>` 占位符，不是越界正文。候选 scope-prohibition 第一遍也明确说明不可检索，但未命中原关键词，记为代理假阴性。不改原分数，不通过修评分表制造提升。

### 采用决策

保留确定性的完整片段预算、引用撤销与真实 Read 后的简短分层约束，作为可回退的本地工程修正。后者仍是提示/输出预算策略，不是已证实有效的质量提升。
不启用动态自查，不增加额外模型调用，不放宽引用或验证门，不改用 Adapter，也不在这个小步骤中追加训练。

结论：本步工程实现和固定对照已经完成；整轮“4B 稳定自主完成文档与本地文件组合检查”目标没有达成。
完整原始记录、summary.json 和逐题 review.md 保存在 `artifacts/prompt-live/compact-evidence-paired-20260915-run3/`，不进入产品包或 Git；本文保留指标和复核结论。

## 距离整轮完成还有什么

剩下的是质量与采用决策，不是继续铺设框架：确认小证据包是否改善组合任务；确认同模型验证的误拒/误放边界；决定保留哪些默认行为并写清不支持场景。
如 4B 仍无法稳定同时完成文档检索与本地检查，应保留已验证的工程边界，把组合任务列为限制，不继续无上限增加 Prompt、调用次数或自查轮次。
本轮不承诺所有组合任务必然成功，不标记 Frozen，不推送、不发布。

建议在这里停止扩大本轮范围：优先以单独 RAG、显式文件读取等已验证的有限流程使用 4B；组合任务不能默认标成已完成。
如果以后继续追求组合任务成功率，需要另立小实验，先区分“任务步骤遗漏”和“语义验证质量”，独立验收，而不是认为再加一次自查就能结束。不存在可信的“只差最后一个补丁”估计。
