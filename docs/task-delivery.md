# 显式任务交付记录

复杂任务可以用 `/task` 建立一份由实际工具回执支持的交付记录，区分“模型说完成了”和“文件、检查结果确实存在”。普通聊天默认不启用，不增加模型调用；它也不是新的规划器或自动续跑机制。

## 使用方法

在当前工作区准备 `task.json`，然后输入：

```text
/task start task.json
```

随后正常向 Agent 描述任务，例如：

```text
完整读取 spec.md，按规范修订 importer.mjs，补 importer.test.mjs，在工作区运行 node importer.test.mjs，最后写 MIGRATION.md。不要修改 raw.txt。测试全部通过后打印 IMPORTER_TEST_OK。
```

审批仍按现有规则进行；契约中的命令不会自动运行，保护列表也不构成权限授权。结束后，TUI 和 inline 显示同一份交付摘要。随时查看或清除：

```text
/task status
/task resolve <operation-id>
/task clear
/context status
```

`status` 在空闲时重新核对文件版本，能够发现用户在 Agent 外部编辑文件造成的检查过期。执行中显示最近一次已观察到的快照。`clear` 只清除交付记录，不删除文件。已有记录必须先清除，才能创建另一份记录。

## 契约格式

```json
{
  "schemaVersion": 1,
  "title": "导入脚本修订",
  "requirements": [
    { "id": "spec", "label": "读取规范", "kind": "read", "path": "spec.md" },
    {
      "id": "script",
      "label": "生成脚本",
      "kind": "artifact",
      "path": "importer.mjs",
      "contains": ["filter"]
    },
    {
      "id": "test",
      "label": "执行回归",
      "kind": "check",
      "command": "node importer.test.mjs",
      "paths": ["importer.mjs", "importer.test.mjs"],
      "outputContains": ["IMPORTER_TEST_OK"]
    }
  ],
  "protectedPaths": ["raw.txt"]
}
```

三类要求的含义：

| 类型       | 认可的实际证据                                                                                                  | 不足以证明的事情                       |
| ---------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `read`     | 成功 Read 返回完整行范围、未截断，并与当前完整文件 hash 一致                                                    | 模型是否正确理解；分页分别读取尚不合并 |
| `artifact` | 成功 Write/Edit/Patch，或工作区 Shell 产生实际文件变化；文件可读取且包含指定文字                                | 整体内容、算法或业务逻辑是否正确       |
| `check`    | 实际工作区 Shell 命令与契约逐字一致，正常退出且退出码 0，回执未截断，前后声明文件版本一致，包含所要求的输出标记 | 用例是否充分；输出标记是否具备业务意义 |

`contains` 和 `outputContains` 是字面结构检查，不是语义裁判。推荐给测试添加“全部断言通过后”才输出的成功标记；不要仅凭退出码 0 声称所有测试执行了。该标记也不能阻止恶意或错误的测试脚本伪造成功，因此仍需审阅测试代码。

`paths` 必须列出该检查所依赖的全部重要文件。漏掉配置、锁文件或测试数据，会让相应变更无法使旧检查过期。第一版只支持明确文件，不递归监视目录；不适合用来证明完整仓库、数据库或远程服务的状态。

## 状态与边界

- **未执行**：没有匹配的实际回执，模型声称完成不会改变此状态。
- **已读取、已有产物、已检查**：分别满足上述有限检查。
- **受阻**：匹配操作被拒绝或工具失败。不会自动重试或绕过 Hook。
- **未知**：部分读取、回执截断、文件无法核对、检查成功标记缺失等。
- **已过期**：对应文件内容 hash 已变化，需要重新读取、生成或检查。

失败、取消、输出 `length/max_tokens` 截断或预算提前收尾不会显示契约已满足。已经成功的副作用仍保留为部分事实。保护文件在已观察到的前后快照中发生变化后，即使恢复原文也保留异常；这不是持续文件监控，不能发现两次快照之间发生又恢复的瞬时变化。

契约最多 32 KiB、8 个要求、32 个不同文件，每个文件最多 2 MiB 且为有效 UTF-8。文件路径必须是工作区内相对路径，复用敏感路径与 symlink/junction 检查；保护文件必须在开始时存在。目录、二进制、大文件或不可读取文件不能成为已核验的证据。

交付记录作为可选字段随 Session 原子保存，旧会话没有该字段时保持原样。恢复的是有界任务记录，不是运行中的进程、模型流或审批授权。新会话没有原任务；恢复原会话后，文件 hash 会重新核对，变化或不可核对的检查不能继续显示有效。不会自动读取并替换成磁盘上后来修改的 `task.json`；要改变契约请清除后重新创建。

新代码兼容没有交付字段的旧会话，不保证旧版程序能读取包含新字段的会话。回退程序版本前请保留会话备份，不要用旧版强行覆盖新会话；本轮尚未更新公开 npm 包。

RAG 引用仍由原有证据校验链负责，尚不作为 `/task` 的 `read` 要求；Skill 的规划文字和 Subagent 自述也不直接成为交付回执。

## 未决操作与恢复

启用了任务记录时，经过模式、Hook 和审批的非只读工具在执行前保存一条 pending 记录；实际完整成功回执到达后移除。保存失败时本次工具不执行，并关闭本轮后续工具访问。恢复时仍未决的记录变为 unknown，不能因文件恰好存在而假定该操作完整成功。

契约中的验收命令有一个严格区分：命令逐字匹配、工作区 cwd、正常退出且明确非零退出码、回执未截断、全部受管理文件前后版本一致时，属于**已知测试失败**，不是执行结果不明。该操作的 pending 可移除，但检查仍为受阻/error，不能满足契约；允许 Agent 在原授权范围内修复并重新申请执行验收，不自动重跑。任意其他 Shell 失败、文件变化、超时、取消、缺失退出码或截断继续保留 unknown，要求人工检查与 resolve。此判断不是全盘文件系统监控，也不证明范围外完全没有副作用。

```text
/task status
/task resolve <operation-id>
```

先检查有关文件或服务，再用 `resolve` 并精确输入 `y` 确认已检查影响。确认不认证成功、不执行工具、不提升权限；后续如需重新尝试，仍要通过原有权限、模式和 Hook。取消确认保留原记录。清除含未决操作的记录同样要求确认，因为这会移除恢复保护，且不会撤销副作用。

恢复本身不调用 Provider 或重放工具。有未决副作用时，后续非只读工具一律在审批前拒绝，不能通过改写命令绕过；遇到拦截或新回执不完整时，关闭本轮后续工具访问。新的回合可使用真正的只读工具检查文件与服务，再由用户确认。Shell 整体属于 execute，包括看似只读的 Shell 命令也暂停，可在应用外手动检查。指纹只用于关联原操作，不是通用幂等键或 exactly-once 服务；Hook、数据库和远程服务仍需各自的事务、查询或幂等设计。

使用已有会话存储的锁、原子文件替换、大小与私有权限策略。交付状态额外最多 128 KiB、16 个未决操作，不包含文件正文或实际工具输入；契约自身仍含用户声明的命令、标记与相对路径，和普通聊天历史一样本地明文保存，不应放秘密。审计不保存这些内容。状态结构损坏或工作区不匹配会明确报错，不静默丢弃任务并显示 healthy；本地状态文件不是密码学认证的执行证明。

关闭自动保存或直接使用未配置持久化的 Engine 时，只能保证内存观察，不能保证强制退出后恢复。`/save` 可显式保存；磁盘写入失败会显示 degraded。任务记录不保存权限，已有用户明确配置的会话/工作区权限策略仍由原权限模块负责。

只对启用的任务在每次请求前注入一份有界状态摘要，不重复复制完整契约、源码或旧摘要进历史。摘要中的 `checks` 提供用户契约原命令，默认工作区示例为 `{"command":"..."}`，优先省略不需要的可选字段；结构化 `workingDirectory: {"type":"workspace"}` 和已激活 Skill 的选择方式仍合法，不改实际 schema。命令提示数组独立限制为 2 KiB，超限整项省略并记录 `checksOmitted`，不截断命令、不减少契约要求。这不是白名单或审批授权，被拒绝的检查仍保持受阻，不能因摘要再次显示命令就重试。

`locations` 只列用户契约中读来源与产物的相对路径、类型和当前状态，不包含正文；数组独立限制为 2 KiB，超限整项省略并记录 `locationsOmitted`。`focus` 根据真实回执提示当前优先阶段：`read-sources`、`produce-artifacts`、`run-checks`、`report` 或 `inspect-blockers`。已知文件可直接 Read，已有完整且当前的来源不重复读；额外读取或发现应有明确的缺失事实或独立能力理由。阶段提示不是工具白名单、强制执行顺序或授权，仍允许合法的补充调查与多 Skill；工具关闭时只能如实报告，不能按阶段提示补执行。

`receiptRequirementsComplete` 只表示当前读/产物/检查回执齐全、保护检查未发现变化且无未决操作，用于提醒及时收尾；不认证内容正确，也不替代最后的回合终态、版本核对或严格满足条件。普通聊天不增加摘要或模型调用；不默认触发第二个裁判、自动续跑或补做。最终本地摘要提示未知与未完成项。

Skill 正文只在当前回合激活。恢复任务与文件回执，不等于恢复了上一回合的 Skill 正文。恢复任务且本轮还没有激活 Skill 时，如果 Skills 与隐式激活已开启、激活工具可用、工具窗口未关闭，Runtime 会增加短提示：用户要求使用工作流续作时，必要读取后应先 `ActivateSkill`，再生成产物、最终检查和报告；`DiscoverSkills` 只返回候选元数据。实际激活后撤下该提示。它仍由模型判断是否适用，不是强制执行门、自动激活或旧 Skill 重放；不新增请求、不授予权限，不绕过 Hook 或审批。无关提问、用户禁止使用 Skill 或工具已经关闭时，不应为了满足提示而补调用。

工具输入校验失败时不执行工具，返回最多约 2 KiB 的诊断和有界纠正提示；不会把 `workingDirectory` 字符串自动改成路径或自动重试。后续纠正必须由新的模型调用提出，继续遵守模式、Hook、审批和剩余预算。发送给 Provider 的严格工具 schema 保留根级 `additionalProperties:false`，本地校验仍是实际执行门槛。

宿主在执行前拒绝非法输入时，不会用这次未执行的尝试覆盖已有有效回执；错误事件和失败统计仍保留，也不会凭空生成新的产物或检查回执。文件版本仍会重新核对，外部修改照常使旧回执过期。已经进入执行或具有未决操作的失败不适用这个规则，仍按实际失败和恢复边界处理。

`Patch` 必须提供 `path`、最近一次 Read 返回的 `expectedHash` 和 `operations: [{oldText, newText}]`；不接受统一 diff 字符串，也不自动转换其他编辑工具的字段。非法 Patch 返回明确的字段提示，纠正后的新调用仍需正常校验与审批；已有交付满足时应报告，不应为了润色再尝试改文件。

动态摘要的每条 `checks` 还包含完整的依赖 `paths`，与命令共同受原 2 KiB 限制；整项过大时省略提示，原契约和检查要求不变。最终检查须覆盖这些文件的最终版本，包括声明的文档产物。基线检查、文档尚未生成时的检查，以及写入文档之前的成功测试，均不能替代最终检查；依赖文件改动后须实际重新检查。提示不会替模型补执行，也不允许重放被拒绝或未决的操作。

回执齐全时，Runtime 提醒优先返回实际交付报告，停止可选的重复读取、润色和 Skill 后续步骤；明确要求但尚未完成的 Skill 加载或具体缺陷仍需如实处理。此提示不是语义裁判或工具过滤器，不能保证模型遵循。预算或恢复保护关闭工具后，三种 Provider 协议均收到显式 `tool_choice: none`；第三方服务可能不遵守，因此本地工具关闭门继续拒绝任何返回的工具调用，不恢复工具权限或自动延长预算。

## 请求预算

`/context status` 增加上次实际送入 Provider 的请求分项：系统规则、动态规则、任务状态、工具定义、AGENTS、Skills 目录、Skill 工具结果、本轮文件/RAG 工具证据、历史/压缩摘要、其他本轮消息和协议余量。

这些互斥分项相加等于本地输入估算；`@` 直接嵌入的正文等复合用户消息仍计入“本轮其他消息”，不是所有语义内容都已细分。压缩摘要计入历史/摘要，不试图从摘要反推已被压缩的原材料。

普通请求的输出上限与 ContextManager 的输出预留一致：默认取 8,192 和窗口四分之一中的较小值，Engine 的 `context.reservedOutputTokens` 可覆盖默认值。现有 RAG 有证据回答仍保留 512 上限。本地估算不证明服务端实际支持该窗口或输出长度；小模型部署的服务端限制仍需单独确认。缓存用量和精确费用没有可靠回报时仍为未知。

`provider_request_started.budget` 在 NDJSON 中返回数值预算，`delivery_updated` 返回有界交付快照，事件 schemaVersion 保持 1。交付事件会包含用户契约标题、标签和工作区相对文件 hash 回执，不包含文件正文或命令参数；不要在标题和标签中放秘密。审计只保存回合状态、要求类型/状态和保护检查结果，不保存标题、标签、路径、hash 或正文。

## 本地示例

源码仓库 `examples/delivery-importer` 包含初始脚本、规范、数据和契约。以下 PowerShell 命令把它复制到独立临时工作区，不修改源码中的示例：

```powershell
$Repo = (Get-Location).Path
$Demo = Join-Path $env:TEMP ("syzzz-delivery-" + [guid]::NewGuid())
Copy-Item -LiteralPath "$Repo\examples\delivery-importer" -Destination $Demo -Recurse
Push-Location $Demo
node "$Repo\dist\index.js"
```

在会话内执行前面的 `/task start task.json` 与示例任务。检查各项状态和实际文件；退出后使用 `Pop-Location` 回到仓库。这个例子只验证文件工作流，不代表任意真实任务的自然语言成功率。

M2 手测：先 `/save`，退出并在同一目录用 `node "$Repo\dist\index.js" --resume <session-id>` 恢复；`/task status` 应保留回执。修改 `importer.mjs` 后再次查看应显示旧检查过期；新开会话不应继承原任务。未决操作的强制进程退出在自动化临时目录中验证，不建议在重要项目上用破坏性命令试验。
