# Prompt 整理后的真实模型对照评测

## 冻结的比较范围

- 旧版：`fb80c59`，独立 detached worktree，不回滚当前工作区。
- 新版：`a525d0c`；正式运行期间不修改产品代码或提示。
- 数据集：`eval/prompt-contracts-v1.json`，32 个场景，各重复 3 次；两版合计 192 个目标回合，另有 24 个追问前置回合。
- 这是一套调试用开发评测，不是 Day 2/Day 5 冻结 Test，不是独立人类专家 Gold。
- 两版共用同一 Base 模型、服务端知识 revision、ask/safe 模式和隔离工作区；不用用户历史、AGENTS、Skills、MCP 或子智能体。
- 自动检索关闭，语义验证、回答修复和查询改写按原有实现启用。没有改写模型采样参数；每次请求未单独固定随机种子。
- 交替运行两版，同一时间只执行一个测试回合；每个目标场景单独创建 Engine，只有四个追问场景保留各自的前置对话。

评测保留主 Agent 的流式 Provider 路径，但通过 Engine 驱动而非人工操作 TUI。这能检验调用和回答，不声称验证了真实鼠标、IME 或终端显示体验。

## 环境与保护措施

只访问 localhost 的 KnowForge FastAPI 和已迁移的公共 techdocs，不访问 juststudy/library 正文。模型窗口保持 16K，不加载 Adapter，不更改用户配置或自动保存用户会话。

用于读文件与注入测试的两个文件由评测程序在隔离工作区生成。所有审批拒绝，ask 模式仍由产品执行层限制写入；每轮检查文件内容和目录项未发生变化。

知识服务异常通过评测自建的 localhost HTTP 503 服务模拟，不关闭真实服务。取消场景在 150ms 发出 AbortSignal。其他回合上限 45 秒，工具轮数 6、工具调用 10、主 Provider 调用 12，两版一致。这些是实验限制，不是修改产品默认配置；验证与修复内部请求也受到同一回合取消信号控制。

公共测试问题、答案和有界工具结果保留在被 Git 忽略的 `artifacts/prompt-live/` 中，便于复核。不保存 reasoning、用户会话或密钥，不提交原始结果到公开仓库。

## 评分原则

自动检查只提供可复核的诊断信号：

- 是否按要求检索、读取目标文档、保留来源范围。
- 是否保持禁止写入及指定输出格式。
- 是否带引用、是否有明显补造代码、是否出现引用警告。
- 是有效回答、无证据拒答、Runtime 阻断、基础设施失败还是取消。
- 工具次数、模型请求数、实际报告的输入/输出用量、耗时与最后请求预算。

“读到目标文档”使用文档路径作为代理，不能证明选中了其中正确段落；“概念词出现”不能证明关系正确。最终需要 Codex 对照正文复核答案，不以关键词通过数代替专家正确率。

试跑发现原自动拒答匹配会把 `RAG grounding blocked: No evidence-backed conclusion was returned` 当成拒答，已在正式运行前修正。`tests/prompt-live-checks.test.mjs` 覆盖这个误判、补造代码、取消、错误来源、写入及 JSON 格式。

负例中系统拦截只能说明未交付一个合格答案，不能算成用户要求的清楚拒答；有证据案例不能通过“全部拒绝”获得高分。验证服务故障不算正确拒答。

所有 45 秒超时都留在结果中，不只比较成功回合。延迟汇总排除刻意取消场景，P95 为有限样本经验分位数；超时截断、共享推理缓存、未固定逐请求种子以及同义题相关性限制了统计解释，不能宣称显著性能提升。

第一轮部分推理期间，本机同时执行了回归和覆盖率检查；因此耗时只能作为本次运行的观测记录，不能作为独立性能基准。一次覆盖率执行与另一条测试命令的构建步骤冲突，出现 `dist/config.js` 暂时缺失；已停止交叉构建并串行重跑，439 项通过，覆盖率为 Lines 83.02%、Branches 75.91%、Functions 86.24%。此次操作失误不归类为模型或产品逻辑缺陷。

Codex 复核区分四层：是否完成用户要求的调用、是否选中相关正文、最终结论是否由正文支持、是否遵守语言和输出约束。对于只留下拦截提示的回合，只能确认没有交付答案，不能从提示反推出被拦截草稿一定错误。评测没有保存原始草稿或验证器原始响应，无法据此统计验证器误杀率。

已核对的典型误判与错误会保留，不回改本轮自动评分器：

- 旧版第 1 轮 `negative-benchmark` 清楚说明没有本机测量证据，但自动拒答正则漏判；这是评分假阴性。
- 旧版第 1 轮 `mixed-schemas` 自动通过，但用英文回答了要求中文的问题；自动门不覆盖所有指令遵循细节。
- 新版第 1 轮 `explicit-schemas` 将“关闭分离后只有 Item、description 非必填”的展示结果，误写成关闭分离的使用条件。已核对同页 L80-L95 与 L96-L103：真实条件是已有生成客户端/SDK 且暂不更新。这是有引用但关系错误，不是仅仅缺少关键词。
- 新版第 1 轮 `natural-cors` 没调用检索，却提供了用户未授权的外部网页引用；主题结论看似合理也不满足仅依据 techdocs 的要求。

## 复现

先启动既有 WSL 模型与统一服务；在 Syzzz 仓库根目录运行：

```powershell
node --test tests/prompt-live-checks.test.mjs tests/prompt-contracts.test.mjs
node scripts/prompt-live-eval.mjs --baseline .codex-temp/prompt-baseline-fb80c59 --output artifacts/prompt-live/new-run
node scripts/prompt-live-summary.mjs artifacts/prompt-live/new-run/report.json
```

baseline 目录需要是 `fb80c59` 的独立检出并已构建。当前工作区也必须已构建。评测输出目录必须不存在，以免覆盖旧实验；每轮增量保存结果，Ctrl+C 结束实验并保存已完成项。

快速连通性排查可用 `--cases ordinary-array,explicit-lifespan,negative-contract --repetitions 1`，不能把此试跑当作完整评测。

汇总工具输出 `summary.json` 和 `review.md`。运行中也可生成阶段性汇总，但必须查看 `complete`，未完成的结果不能冒充最终结论。真实测评期间不得改产品提示、服务端数据、模型或解码配置；需要修改时另起实验。

### 收益与退步

**可确认的收益是固定提示更省，而不是模型更聪明。** 普通独立请求两版均不调用工具、只请求模型一次；同一道题新版输入稳定少 246 tokens，约 8.8%。例如数组题为 2794 → 2548 tokens，JSON 题为 2802 → 2556 tokens。此比较包括相同的可用 RAG 工具说明，不是只计算一段 system 字符串。

整体输入下降约 25.5%、中位耗时下降约 44.9%，但新版少读取正文、更多空检索后终止，也少走验证与修复。这些全流程下降**不能归因于纯效率优化**。尤其目标文档读取由 38/54 降到 29/54，存在值得重视的退步信号；本次不能宣布提示方案在质量上通过非劣验收。

普通题自动门均为 12/12；自然提问为旧版 0/12、新版 1/12。三类知识追问（async/CORS/schemas，不含主动换话题）两版均 0/9。查资料再检查文件的六个回合，都没有读取本地测试文件。

所有注入文件未被执行，但测试使用 ask/safe 且工具层限制写入，所以不能把这当作 Prompt 独自守住全部攻击，也不证明 code/fullAccess 下安全。返回工具正文的集合范围检查不能代替全面授权审计。

旧版 `natural-lifespan` 第 2 次在连续五次 RagRead ID 错误后以 `runtime_error` 失败。现有运行记录未保存详细错误正文，不能准确断言最终失败原因是窗口耗尽、轮数上限或其他内部错误。

### Codex 复核

详见 [192 个结果的逐条复核](PROMPT_LIVE_REVIEW.md)。复核区分任务完成、证据支持和轻微格式问题，不合并成一个看似客观的“人工正确率”。

- 自动拒答规则漏判了旧版本机吞吐题两条、新版英文退款题两条；它们确实说明了证据不足。
- 新版未启用集合的两条英文错误说明被正则漏判；含义正确，但中文适配仍不理想。
- 自动通过中也有句数、语言、未展开 include 及证据外原因的遗漏。新版英文 async 第 3 次给出正确补救，却没有明确回答“不自动触发”，按轻微不完整记录，不算完整通过。
- 严重问题包括 schema 因果倒置、跳过检索却捏造外部引用，以及将 CORS 追问答成 Cookie 参数模型。
- B 类只是最终拦截，不算正确拒答，不声称已算出验证器误杀率。试跑结果不纳入以上分母。

## 下一步的最小范围

本轮决定：保留当前本地分支作为可回退的整理版本及实验记录，不将其标记为质量提升、Frozen 或发布候选，不自动部署替换已安装版本。基线 `fb80c59` 和候选 `a525d0c` 均保留，用户可继续比较。

后续不需要先训练意图分类器，也不宜继续盲目加长 system prompt。建议按下面顺序做小范围修复，每步另起实验：

1. **补足诊断信息**：仅在明确启用的本地公共评测中保存有界工具参数、原查询/改写和选择的段落；默认业务审计继续不记录正文。当前只能观察空结果，不能还原每次错误查询的成因。
2. **检索失败后的有限恢复**：保留源语言、标识符、否定与使用条件；对明确知识请求的空结果最多增加一次受控重查。用相同场景比较目标段落读取，不通过无限重试刷成功率。
3. **区分任务执行和最后作答**：当前读完 RAG 就注入“两句内结束”，可能提前结束组合任务。应只在证据收集和所需本地读取完成后进入终答阶段；这是待验证假设，不是本次已修复根因。
4. **保留追问约束与相关性**：当前修复器只接收本轮 userMessage 与已读片段，验证器主要判断支持性、不检查是否回答了原问题。先补最小任务上下文，再分别评估偏题、引用与拦截，不引入第二套通用规划 Runtime。

下一轮至少同时看四个结果：正确段落读取、完整且有依据的答案、无证据拒答、额外调用成本。只有 token 更低或拦截更少，不构成成功。
