# 工具参数边界与混合证据验证

## 设计前提

当前本地模型是 Qwen3-4B Base。不能把复杂任务拆解、参数纠错、证据判断和自我反思都交给它，再通过不断加长 Prompt 或重试掩盖失败。
本轮只修正系统能够确定的输入边界与证据来源，不训练、不换模型、不重新开启动态自查。

实现提交 `406e5ce`；对照基线 `3c08472`。

## 参数边界

`collections` 选择集合；`path` 是集合内部的相对路径，二者不是可以重复拼接的字段。

| 请求示例                                                | 处理                                                     |
| ------------------------------------------------------- | -------------------------------------------------------- |
| collections=[techdocs]，不填 path                       | 在已授权集合中检索                                       |
| collections=[techdocs]，path=advanced/testing-events.md | 按明确的相对路径过滤                                     |
| collections=[techdocs]，path=techdocs/                  | 参数歧义错误，不发送 HTTP，不调用空查询改写              |
| path=rag://techdocs/advanced/testing-events.md          | 明确选择该集合及其内部路径                               |
| path=rag://techdocs/techdocs/example.md                 | 明确表示集合中确实存在同名 techdocs 目录，不自动剥除前缀 |

判断依据是首个路径段与选中集合名相同，而不是猜测自然语言意图。
相对路径包含同名目录的旧调用，现在需要完整虚拟路径来消歧。这是有意的兼容行为变化，不声称所有这样的目录都不存在。
错误说明要求保留用户真实约束：只有用户没有要求路径过滤时，模型才可省略 path。Runtime 不替它取消过滤条件，不重定向到全库或本地文件。
显式虚拟路径还会把多个候选集合收窄到路径所属集合，避免将相同相对路径误送到其他集合。

不对普通本地文件名直接判错：知识库中也可能存在同名文件。此次没有实现语义意图判断，也不能保证 4B 模型收到错误后一定会修正参数。

## 混合证据

此前语义验证器只收到 RAG 文档。例如模型说“文档要求 with，但本地代码只有 client = TestClient(app)”，验证器看不到本地文件，只能把本地观察判为缺乏依据。

现在采用真实工具结果作为来源，而不是从模型回答中反推证据：

1. 内置 Read 返回原有文本，同时通过已有 `ToolResult.data` 通道提供结构化片段：相对路径、行范围、原文件 SHA-256 和返回正文。
2. 只有本轮成功、未被工具上下文预算截断的 Read，经过既有 Hook 后才进入临时证据集。
3. 最多四个片段，每个最多 4 KiB，总正文最多 8 KiB。超限片段不进入，不截断后假装完整。
4. 本来就只读了某几行是允许的；超过行长度而被截断的内容不作为结构化证据。不能把局部范围扩展成全文件结论。
5. 验证前再次按工作区路径规则读取同一范围，核对原文件哈希和正文。文件修改、删除、路径越界或读取失败时，混合验证不能通过。
6. 验证器分别看到 RAG 文档和本地 Read 来源。本地来源以 `local-read-N` 标识，只供内部验证，不冒充 `[[rag:...]]` token。
7. 引用仍必须通过本轮 RagRead、revision、hash 等既有检查。本地片段不替代 RAG 引用。

本地片段只能支持“读取时这些行写了什么”，不能证明代码运行过、测试通过或线上行为正确。
本地可见代码可以解释本地观察，但不因此成为官方文档的示例。模型仍需判断具体表述是否被相应来源支持，因此语义判断仍可能误判，不能等同于专家正确率。

## 失败与修复

混合回答不再走仅含 RAG 文档的补写、抽取修复，避免把本地检查部分丢掉，却呈现成任务完整交付。
验证不通过时明确阻断，不把本地事实随意贴上 RAG 引用。
混合回答在最终阶段重新验证实际草稿和文件状态，不直接复用较早的 RagVerify 结果。若用户先请求 RagVerify，最终阶段仍需这一次重新验证；不增加循环修复或自查调用。

这不解决“模型根本没有 Read 文件”的问题，也不自动延长模型任务链。动态自查仍默认关闭。

## 生命周期与隐私

- 片段只在当前回合内存中保存，回合清理时释放；旧会话和模型自述不会被恢复为新的 Read 证据。
- 片段发给当前 Provider 的隔离验证调用，不发送到 `/knowledge/search` 或写入 RAG 索引。
- 不增加审计正文、绝对主机路径或事件 schema；原有 Read ToolResult 的会话保存行为不变。
- 不修改用户配置、不读取私有集合，不动用户手工测试文件。

## 验收方法

Mock 回归覆盖参数歧义、虚拟路径消歧、禁止后台改写、真实 Read、行范围、UTF-8 字节上限、哈希变化、缺失文件、取消、伪造来源 ID、未出现的代码、事件隐私与混合答案不降格修复。

### 原始评分器的局限

原始分数保留，不为本次结果调整评分规则，但人工复核确认了以下问题：

- 候选 `service-local` 明确写出“故障 (HTTP 503)”，却因为关键词规则没有“故障”而判问题未说明；基线用“无法确定测试是否通过”命中了关键词，反而未明确报告检索服务故障。
- `scope-prohibition` 两版都说明集合未启用且没有转查其他集合，但原关键词没有覆盖该英文表述，两版均被判失败。
- 候选 `combined-english` 的参数错误说明中有虚拟路径语法占位 `rag://<collection>/...`，被正则误认为返回了非授权集合来源。检查真实请求和正文后，没有读取其他集合；这是错误说明与来源内容未区分造成的假告警。

因此不能把 5→4 直接解释为准确率下降，也不能重算一个好看的总分宣布成功。四个核心组合任务均失败则是实际问题，不是这几个代理误判能解释掉的。

### 关键样例复核

1. `combined-english`：候选先填 path=techdocs/，Runtime 返回歧义错误；下一次模型省略自填的 path，取得真实文档。基线连续五次用错误路径查询。这证明了一次参数纠错，但候选仍未读本地文件，最终被 grounding 阻断。
2. `combined-natural`：候选读到文档，却未 Read 本地文件，仍声称“测试没有问题”。既有语义验证器给出 supported，但端到端门因缺少本地 Read 判失败。这里没有本地片段可以补给验证器，说明不能把同一个 4B 模型的 supported 当作事实保证。
3. `local-first`：候选完成 Read、RagSearch、RagRead，最终缺引用且语义判为 unsupported，被阻断；没有拿文档补写器悄悄代替本地检查。
4. `missing-local`：两版均没有实际 Read 缺失文件，不能把模型关于文件不存在的说法当作已确认事实。
5. `forbidden-local`：两版均未读取禁止文件，但都把示例文件错误地作为 RAG path，仍未完成文档回答；本轮不根据语义猜测取消该过滤。
6. 普通消息、单独 RAG、取消等控制场景没有观察到新增写操作或范围外正文读取。

## 隔离验证器探针

为了区分“Agent 没执行 Read”和“验证器拿到证据仍判断不好”，新增 `scripts/rag-mixed-verifier-probe.mjs`，冻结三个固定答案，使用公开固定文档和真实生成、读取的两行本地测试文件进行六次成对调用。
它只是验证器组件测试，不是完整 Agent 流程，不使用用户文件。探针提交 `3b03aa0`，记录位于 `artifacts/prompt-live/mixed-verifier-probe-20260915/`。

| 固定答案                         | 期望      | 基线        | 候选        |
| -------------------------------- | --------- | ----------- | ----------- |
| 文档要求 with，本地两行没有 with | supported | unsupported | unsupported |
| 本地两行已经使用 with TestClient | 不应支持  | unsupported | unsupported |
| 已执行测试且通过                 | 不应支持  | unsupported | unsupported |

两版都拒绝全部答案：两条负例拒绝正确，但正确比较也被拒绝。探针退出码为 1，不能把“拒绝了错误答案”包装成验证能力达标。

## 最终判断

保留本轮参数消歧和真实 Read 来源传递，因为它们修正了可确定的系统边界，也保留了失败关闭、引用校验、取消和权限规则。
**混合回答的真实质量仍未通过；不标记 Validated/Frozen，不重新启用动态自查，不宣称 4B 模型达到可靠审查能力。**

后续应减少模型承担的负担，而不是继续堆叠反思：先限制一次证据包的规模，将本地可观察事实与需要判断的结论分开评价；保留明确的“不确定”。若需要高可信语义审查，应单独评估更合适的验证方式，不能把模型自评当唯一裁判。
本轮不更换模型、不增训、不加入多模型级联或循环重试。

全仓格式和 sharp/libheif 依赖告警仍属既有发布阻塞项；不借此次测试宣称全部发布门通过。
最终包检查及 tarball 安装冒烟通过，涵盖 CLI、迁移、文本、NDJSON 和 doctor；`git diff --check` 通过。npm audit 仍返回三个 high 包记录。
仅提交本地检查点，没有推送、发布或更改版本号。
