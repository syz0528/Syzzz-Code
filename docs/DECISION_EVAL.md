# 任务理解与路由决策评测报告

日期：2026-09-21。结论：**完成本轮诊断，暂不接入前置模型或自动路由。**

本报告中的产物路径均相对于 Syzzz Code 仓库。用户授权 Codex 代审，本轮复核不是独立人工 Gold。没有修改产品默认行为，没有重训 KnowForge，没有推送或发布。

## 1. 先说结论

本轮问题不主要表现为“不知道该查知识库”。在 19 个需要 RAG 的真实开发场景中，三个方案都发起了检索；在 20 个不需要 RAG 的场景中，三个方案都没有无必要检索。

但检索发生之后，仍出现查询或选片不对、回答偏题、漏读本地文件、只读到文件第一行就停止、引用截断、验证阻断等问题。提供正确的需求字段，没有使这些任务更可靠地完成。

因此，本轮支持的决定是：**先修检索和任务完成链，不把额外模型放到每个环节。** 这不是证明所有意图识别器无效，也不是证明 Jev 无效。Jev 本轮未实测。

## 2. 实际做了什么

1. 固定 40 条开发题、80 条保留题，按 FastAPI 文档主题家族隔离；保留题没有送入模型。
2. 整理首批 12 条可阅读标注样例，由 Codex 按用户授权代审。
3. 建立隔离评测入口，复用既有 QueryEngine、Provider、RAG、查询改写及验证链。
4. 运行 40 条开发题的三组对照，共 120 个目标回合。
5. 补充 40 条决策筛查：确定性规则与本地 4B 的结构化判断，不改变 Agent 流程。
6. 复核全部 120 份最终输出及工具摘要，对关键失败追查原始工具结果、草稿和源码；保留原始自动分与复核分。
7. 按停止条件关闭候选上线和冻结集扩测，提交本报告与可复算产物。

120 个回合包含 117 个真实任务回合，以及同一 HTTP 503 注入场景的 3 个方案回合。故障注入不计入真实任务正确率。

## 4. 具体失败发生在哪里

### 4.1 已经检索，但找错问题的证据

`dev-explicit-lifespan` 三组均检索并读取了片段，但主要依据 release notes 和 lifespan 定义回答，没有说明测试中的 TestClient + with。验证器甚至给出了 supported。

独立使用参考查询 `TestClient lifespan with statement` 能找到 `advanced/testing-events.md` 的明确句子。说明语料中有答案，不能把问题简单归为“知识库缺资料”。

这也说明：**结论被某段资料支持，不等于回答了用户的问题。** 本轮只记录了有界搜索结果和读取结果，没有完整的查询及交付 receipt 跟踪，因此不能对每个失败强分“查询生成错”还是“排序/选片错”。

另一个已确认的机制是 `src/rag/runtime.ts` 约 1189–1198 行：首次检索非空就直接返回，只有空结果才进入查询改写。因此“返回了低相关片段”不会自动触发来源语言改写。这是后续相关性实验的具体切入点，不是增加一个“需要 RAG”标签即可修复的问题。

### 4.2 正确需求提示没有保证执行完整

全部 15 个组合回合均未完整交付两个结果。提示组的 CORS/query 案例实际调用了 Read，但结果明示 `Lines: 1-1 of 2`，并提示从 offset 2 继续。模型仍将第一行注释当成完整文件，声称没有 SETTING。

因此，“工具执行成功”不能等同于“证据收齐”。这是后续完成检查应针对的具体对象，不需要先增加一个通用意图分类器。

### 4.3 现有动态提示存在潜在冲突

`src/runtime-engine.ts` 约 1819–1838 行：已有 RAG receipt 时，在未启用实验性完成自查且未读到本地证据的分支，要求两句短回答后停止。约 1865–1872 行进一步收紧输出预算，约 1959 行还设置空行 stop sequence。

正确需求提示作为 systemPromptSuffix 进入较早层级，而上述规则仍在每轮动态装配。它可能促使组合任务过早结束，也可能参与输出截断；本次没有修改这些规则，所以不能声称已通过消融证明具体因果。

下一次应在同一小组失败用例上单独对照该规则，不能一边调提示、一边换模型、再一边加路由后只看总分。

### 4.4 搜索需要与直接读入证据是两回事

无证据商业条款题，基线有 3/4 正常拒答；提示与预检索均为 0/4。预取技术片段并不会凭空产生合同证据，却会进入引用与语义验证路径。

这支持检查“候选是否适合读入”和“准确表达证据不足”的边界，不支持用“需要 RAG=true”直接代表“应注入任意前四条”。不能仅因最终被阻断，就断言验证器是错的；必须分别检查原始草稿、证据与验证结论。

### 4.5 故障降级单列

三个方案都面对合成的 HTTP 503。基线和提示组由 RagSearch 返回错误后，助手说明服务不可用；预取方案直接结束为 runtime_error，并携带准确的 HTTP 503 错误，无助手正文。

这不是服务随机宕机，也不是隐藏了错误。它暴露的是预取发生在 Agent 回合前时，错误恢复路径不同；如果未来采用路由，应先明确其降级合同。

## 5. 自动评分为什么调整

原始 40 条口径自动分为 26、22、21，包含故障题；复核不修改原始 report.json。

四处自动误判被单独纠正：

1. 基线 lifespan 澄清：输出有“哪一个”，实际却先用 Grep 查看了两份文件，没有真正请求用户确定对象。
2. 提示组显式 CORS：完整引用后又增加无关结论，并留下截断的第二个引用。
3. 预检索隐式 CORS：全英文，违反明确中文要求。
4. 预检索 dependency 澄清：宣称将读取两个文件，没有真正请求澄清。

轻微语言问题单独保留，没有全部判失败。例如本地值回答使用英文，但该题没有明确中文格式要求，且文件与值均准确，维持通过。

全部结果、复核说明和配对清单见 `artifacts/decision-eval/dev-oracle-20260921/codex-review.md` 与 `codex-review.json`。

## 6. 独立决策筛查

此步骤是停止扩测前的小规模诊断，不是唯一候选已经入选或已完成端到端验证。

| 指标，40 条                              |   简单规则 | 本地 4B 隔离判断 |
| ---------------------------------------- | ---------: | ---------------: |
| rag/local/clarify/collections 四字段全对 |      38/40 |            21/40 |
| 五字段全对，含 action                    |      38/40 |             4/40 |
| 输出合同不合法                           |          0 |                5 |
| 模型请求                                 |          0 |               40 |
| 决策请求 P50 / P95                       | 未单独测量 |  1.137 / 1.531 s |

注意 action 的标注约定过粗：文档解释题统一标为 inspect，但模型返回 explain 也有合理性。因此五字段 exact 只保留原始诊断，**不把 4/40 当作模型只有 10% 意图理解能力**。即使排除 action，仍只有 21/40 完整满足证据需求合同。

规则主要失败在两条已消歧追问，没有利用历史恢复本地对象；其余模板措辞非常规整，因此 38/40 不代表真实对话中的泛化能力，更不构成上线理由。

本地模型把部分“只改写给定文本”判断为需要本地文件，把部分明确读文件题判断为不需要本地证据。五个组合题均出现集合字段校验失败；原始错误输出正文未保留，不能断言它具体生成了哪种错误集合。

有效 35 次决策请求记录到 8,428 输入、800 输出 tokens；5 次合同校验失败未保存 usage，因此这不是全部 40 次的总成本。后续完善采集器应先记录 usage 再做 schema 校验。

Jev：本次环境未配置可用专用凭证，未调用、未测速、未计费，也没有推断其优于或劣于当前方案。

## 7. 测量边界和未完成项

- 本轮先行开发集实验，不是生产验收；没有执行保留集 80×2×2 的 320 回合配对测试，因为前置诊断未支持继续。
- 80 条保留题只冻结文本和划分，尚未运行、未通过、未完成独立证据标签逐条验收。
- 单一公共集合、ask/safe、Python 两行文件、模板化技术问题；没有覆盖多集合选择、写任务、真实企业复杂历史或完整 AskUser UI。
- 没有独立专家 Gold，没有跨模型、跨硬件重复，也没有测试所有取消/超时组合。
- 首字采集目前是“主模型首个正文”，可能是之后被验证拦截的草稿，**不是首个有效用户可见回答**。原始值保留为 proxy，不宣布首字改善。后续应增加实际交付事件时间戳。
- `evidence` 路径记录处于 readChunks 返回阶段，不能单凭路径证明该片段最终完整进入模型上下文；本轮结合工具结果复核关键案例，未声称测得完整上下文装配召回率。
- 工具错误包括非法 chunk ID 和预算未交付等，不能全部叫作参数 JSON 错误。底层 malformed_response 另列。
- 没有观测到文件修改、禁止工具成功或远程外发；这来自严格隔离环境，不能称为生产安全认证。

早期 6 个冒烟回合曾因采集器把 Provider 的 text 字段误写为 delta 而失败，已纠正并重新通过 6/6；失败轮保留在 `smoke-20260921`，不并入正式分数。正式三组对照未中途修改代码或挑选重跑。

## 8. 下一步建议，尚未实施

优先级按本轮事实排序，保持小范围单变量修改：

1. **补观测**：记录有界实际查询、候选选片与最终交付状态，以及用户可见回答首字；仍只用于公开实验，不扩大产品隐私日志。
2. **检索相关性**：用 lifespan/form/query 的小组固定题对照中文原问题与来源语言查询；区分没有召回、错误选片、预算未交付。
3. **组合任务收尾规则**：检查“读取 RAG 即停止”与尚未读取的本地部分是否冲突；针对 `More content available` 继续读取，不把成功工具名作为完成证明。
4. **拒答与验证**：区分没有证据、检索故障、回答不受支持；验证 supported 不代表相关且完整。
5. 上述基线改善后，再做需求提示消融；只有出现可重复净收益，才考虑规则或小模型候选，再启用保留集。

本轮没有启动这些产品改造，避免把“诊断实验”和“为使实验好看而修系统”混在一起。
